# 第四轮研究：SH 多类别提取（不合并到主分支）

目标：验证官方 Semantic Hearing 39.pt 在**无人手动选择单一警告类别**的固定配置下，能否同时保留 car_horn 和 siren，并比较速度及音质。实验不声称实现自动危险识别。

## 实际需要区分的能力

1. 官方代码读取20维的 **one-hot** 类别向量；是否能处理同一向量两个1（two-hot）？**程序接受不代表训练过，也不等于音质好。**
2. 用 two-hot 单次连续模型推理，能否保留**两种不同音效**，特别是两者重叠时？
3. 若不可行，两次独立流式推理（car_horn、siren）并直接相加，能否保留两者？计算成本、背景泄漏和音频峰值怎样？
4. 只存在喇叭或只存在警笛、只有背景时会怎样？通过单目标对照和背景能量验证。
5. 这是否意味着能自动识别所有危险声音？**不能。** 固定多目标提取无需用户逐次选择，但不等价于语义危险判定；自行车铃没有在本轮覆盖。

## 固定范围

- 保留官方Net、源码SHA与之前三轮严格验证的39.pt权重；没有训练。
- 采用第三轮已验证的 StatefulHearing，416新采样一块，保存encoder、decoder、output全部状态，不按事件启动或清零，不重启SH。
- 原始素材只复用已在第二轮保存并核对ZIP哈希的双声道真实录音成分：汽车喇叭0257、0260，IUSB警笛和雨声/道路背景。
- 六段8秒混音：单喇叭／单警笛／先后发生／两种不同的同时重叠／纯背景；背景五秒原段循环扩展，因此不是完整独立八秒自然道路录音。
- 每段前三种方法真的运行SH。第四种“两次相加”只是两次单类输出的算术合成，不是第三条模型调用。
- 所有输入/输出维持同一原始FLOAT波形幅度；保留每个目标的真值参考、每段目标投影增益、SI-SDRi、前100ms、背景泄漏、推理RTF。
- 使用文件流并测CPU运行耗时，**不是手机/耳机实时听音测试**。

## 运行

由独立分支的GitHub Actions工作流（research-sh-round4-multiclass.yml）执行；严格加载官方权重，运行结构测试与真正连续音频处理。工作流将报告、JSON和小型试听包提交至evidence目录，完整浮点WAV保存为GitHub Actions artifact（90天）。

本地运行需与第三轮一致的依赖环境、固定官方源码和官方权重：

    python -m unittest discover -s research/semantic_hearing/round4 -p 'test_*.py' -v
    python research/semantic_hearing/round4/study.py --semantic-repo /tmp/SemanticHearing --checkpoint /tmp/39.pt --output /tmp/sh-r4-run --evidence research/semantic_hearing/round4/evidence

## 数据解释

- “目标投影增益接近0dB”只说明目标幅度保留较好，必须同时考虑失真和背景噪声；SI-SDRi与质量不能互换。
- 单次two-hot成功推理不证明训练方案支持多标签，更不能作为安全产品证明。
- 双次模型推理的总耗时在服务器实测；未来实际手机性能、端到端播放延迟未测。
- 普通立体声原始素材没有验证是耳部采集的真双耳；IUSB目标可能含其他原始背景噪声。
- 所有连续实验预先指定两类，**没有实现任意声音的自动分类或自行车铃**。
- 若无预训练运行输出，不得声称已经完成音质实验。只有CI绿灯、结果文件及实际WAV的哈希完整时才称完成。
